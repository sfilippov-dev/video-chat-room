# Implementation Plan — Видеочат-комната (`video-chat-room`)

| | |
|---|---|
| **Документ** | Implementation Plan (IP) |
| **Версия** | 1.0 |
| **Вход** | [`prd-video-chat-room.md`](./prd-video-chat-room.md) (PRD v1.0), [`design-video-chat-room.md`](./design-video-chat-room.md) (TDD v1.0) |
| **Шаблон** | `rules/prd-tasks.mdc` |

**Как читать.** Задачи идут строго по порядку: каждая следующая опирается на результат предыдущей. Каждая задача атомарна (≤ 1 часа), заканчивается работающим состоянием проекта и одним коммитом. `_Requirements_` — номера пунктов раздела 4 PRD и ID user stories; `_Design_` — номера разделов TDD.

**Порядок работы над задачей:** объявить, что и в каких файлах → сделать → проверить, что проект поднимается → отметить задачу здесь → коммит.

**Режим остановок:** коммит после каждой задачи, отчёт и остановка — **после каждой фазы** (одна строка на задачу + общий список для ручной проверки). Исключение: **после задачи 16 и после задачи 18** останавливаемся отдельно — это критичные места (деградация соединения и освобождение камеры).

**Легенда областей:** `DevOps` · `Backend` · `Frontend` · `Тесты` · `Документация`.

## Фаза 1. Сервер

- [x] 3. **Валидация входных данных** · `Backend` `Тесты`
  - Серверная валидация имени, текста сообщения и `roomId` по белым спискам — клиентской недостаточно.
  - 3.1. `server/src/validation.js`: `validateName` (trim, 1…30, `/^[\p{L}\p{N} _-]{1,30}$/u`), `validateMessage` (trim, 1…1000), `validateRoomId` (≤ 64, `[A-Za-z0-9_-]`).
  - 3.2. Unit-тесты (Vitest): пусто, одни пробелы, 31 символ, `<script>alert(1)</script>`, кириллица, эмодзи.
  - _Requirements: 24, 38, US-1, US-8, Design: §4.1, §5.4, §10.2, §10.3, §11.1_

- [x] 4. **Хранилище комнат в памяти** · `Backend` `Тесты`
  - `rooms: Map<roomId, {participants: Map, messages: []}>` и синхронные функции над ним; модуль не знает про Socket.io.
  - 4.1. `server/src/rooms.js`: `getOrCreateRoom`, `tryAddParticipant` (**проверка лимита и вставка в одном синхронном блоке, без единого `await`**), `removeParticipant` (удаляет комнату целиком при опустевании), `setMediaState`, `addMessage`, `getParticipants`, `getMessages`, `hasParticipant`.
  - 4.2. Unit-тесты: создание комнаты первым участником; вход по неизвестному id создаёт комнату; 4 входят, 5-й получает `ROOM_FULL`; выход последнего удаляет комнату **и историю**; повторный вход по тому же id даёт пустую историю; одинаковые имена сосуществуют.
  - _Requirements: 5, 7, 8, 9, 30, US-5, US-10, Design: §4.1, §4.3, §5.2, §5.3, §11.1_

- [x] 5. **Обработчик `join`: вход, лимит, ack** · `Backend` `Тесты`
  - Атомарный вход в комнату с ответом-вердиктом; старожилы получают команду инициировать соединение, новичок — список тех, от кого ждать оффер.
  - 5.1. `server/src/socket/handlers.js`: обработчик `join` — валидация, `tryAddParticipant`, `socket.join(roomId)`, `socket.data = {roomId, name}`.
  - 5.2. Ack: `{ok:true, selfId, participants, messages}` либо `{ok:false, code:'ROOM_FULL'|'INVALID_NAME'|'INVALID_ROOM'}`.
  - 5.3. Рассылка старожилам `peer-joined` (новичку **не** отправляется) и `participants` всем.
  - 5.4. Интеграционный тест: при 3 участниках два `join` в одном тике → ровно один `ok`, второй `ROOM_FULL`.
  - _Requirements: 1, 4, 5, 7, 8, 26, US-4, US-5, Design: §3.4, §4.3, §6.3, §7.1, §7.2, §11.2_

- [x] 6. **Выход и обрыв соединения** · `Backend` `Тесты`
  - Один и тот же код на кнопку «Выйти» и на разрыв сокета: сервер не различает выход и обрыв.
  - 6.1. Обработчики `leave` и `disconnect` (идемпотентные): `removeParticipant`, рассылка `peer-left` и `participants`.
  - 6.2. Системное сообщение с кодом `'left'`; формулировка «соединение потеряно» не используется нигде.
  - 6.3. Интеграционный тест: `disconnect` освобождает слот, остальные получают `peer-left`; после ухода последнего комната удалена.
  - _Requirements: 9, 27, 28, 31, US-10, US-11, Design: §5.2, §5.3, §7.6, §11.2_

- [x] 7. **Реле сигналинга WebRTC** · `Backend` `Тесты`
  - Сервер перекладывает конверт `offer`/`answer`/`ice`, не парся SDP.
  - 7.1. Обработчики `signal:offer`, `signal:answer`, `signal:ice`: подмена `targetId` → `fromId`, отправка адресату.
  - 7.2. Проверка «отправитель и адресат в одной комнате», иначе событие молча дропается.
  - 7.3. Интеграционный тест: оффер доходит до адресата; сигнал в чужую комнату не доходит.
  - _Requirements: 10, Design: §3.3, §6.3, §7.2, §11.2_

- [x] 8. **Состояние микрофона и камеры на сервере** · `Backend`
  - Флаги устройств живут на сервере и рассылаются остальным — индикация не «домысливается» по факту прихода потока.
  - 8.1. Обработчик `media-state`: `setMediaState` + broadcast `peer-media-state`.
  - 8.2. Значения по умолчанию при входе: `micOn: true`, `camOn: true`.
  - _Requirements: 13, 15, 16, 18, Design: §5.2, §6.3, §6.4_

- [x] 9. **Чат на сервере: сообщения, история, системные события, анти-флуд** · `Backend` `Тесты`
  - Сообщения кладутся в историю комнаты и рассылаются всем, включая автора; новичку история отдаётся только в его сокет.
  - 9.1. Обработчик `chat:send`: trim, валидация, `ts = Date.now()`, имя берётся **из серверного состояния**, а не из payload; broadcast `chat:message` всем участникам.
  - 9.2. Системные сообщения `chat:system` (`'joined'` / `'left'`) кладутся в ту же ленту `messages`.
  - 9.3. Анти-флуд: токен-бакет 5 сообщений / 2 с и 30 / мин → ack `RATE_LIMITED`.
  - 9.4. Интеграционный тест: новичок получает историю только себе (у остальных лента не дублируется); имя из payload игнорируется; флуд отсекается.
  - _Requirements: 21, 22, 23, 24, 25, 40, US-8, Design: §5.2, §6.3, §7.5, §10.3, §10.4, §11.2_

## Фаза 2. Клиент: вход и медиа

- [x] 10. **Стартовый экран и роутинг** · `Frontend`
  - Ввод имени, создание комнаты по `crypto.randomUUID()`, вход по ссылке `/<roomId>`.
  - 10.1. Роутинг `/` и `/:roomId` (две роуты), `App.jsx`.
  - 10.2. `JoinScreen.jsx`: поле имени `maxLength = 30`, счётчик символов, клиентская валидация, кнопки «Создать комнату» / «Войти».
  - 10.3. Проверка поддержки WebRTC (`RTCPeerConnection`, `navigator.mediaDevices`) до входа → сообщение «Браузер не поддерживает WebRTC».
  - 10.4. Никакого `localStorage`/`sessionStorage`: имя между перезагрузками не запоминается.
  - _Requirements: 1, 2, 4, 28, 36, 38, US-1, US-2, US-4, US-13, Design: §4.2, §5.4, §5.5, §7.1, §8.1 (E-1…E-3, E-12)_

- [x] 11. **Локальные устройства: `LocalMediaController`** · `Frontend`
  - Захват камеры и микрофона с деградацией: пользователь попадает в комнату при любом исходе.
  - 11.1. `client/src/lib/LocalMediaController.js`: `init()` с constraints 720p `ideal`, единый объект `MediaStream` на всю сессию.
  - 11.2. Разбор ошибок: `NotAllowedError`, `NotFoundError`, `NotReadableError`, `OverconstrainedError` → флаги `hasMic/hasCam`, `micOn/camOn`, текст ошибки.
  - 11.3. **Потеря устройства во время звонка (требование 20).** На каждую полученную дорожку вешается обработчик `ended` (камеру выдернули, устройство перехватило другое приложение, ОС отобрала доступ). Реакция: остановить соответствующий поток корректно — `track.stop()` для подстраховки, `sender.replaceTrack(null)` на всех соединениях для видео и `enabled = false` для аудио, сбросить `camOn`/`micOn` в `false` и снять флаг `hasCam`/`hasMic`, разослать `media-state` на сервер. Автоматических попыток перезахватить устройство нет — восстановление выполняется пользователем через настройки браузера/ОС (PRD п. 20).
  - 11.4. `stopAll()` для выхода и для отказа в слоте.
  - _Requirements: 13, 14, 20, 33, US-6, US-7, US-12, Design: §4.2, §8.2, §8.4, §9.5_

- [x] 12. **Сессия комнаты: `useRoomSession`** · `Frontend`
  - Конечный автомат `idle → acquiring → joining → in_room` и оркестрация сокета, медиа и состояния.
  - 12.1. `client/src/hooks/useRoomSession.js`: порядок «клик (жест пользователя) → `getUserMedia` → `socket.connect()` → `join` с ack».
  - 12.2. Разбор ack: `in_room` / `rejected` (`ROOM_FULL`) / `server_error`; при `ROOM_FULL` — немедленный `stopAll()` и отключение сокета.
  - 12.3. Хранение списка участников и их `micOn/camOn` из событий `participants` и `peer-media-state`.
  - _Requirements: 8, 26, 35, 37, US-5, US-13, Design: §4.2, §7.1, §8.3, §8.6, §8.7_

- [x] 13. **Видеосетка и self-view** · `Frontend`
  - Каркас экрана комнаты и собственная плитка до того, как появятся удалённые потоки.
  - 13.1. `RoomScreen.jsx`, `VideoGrid.jsx` (CSS Grid: 1 / 2 / 2×2), `VideoTile.jsx` с оверлеем имени.
  - 13.2. Self-view: `<video autoPlay playsInline muted>` — `muted` обязателен (иначе эхо и свист).
  - 13.3. Удалённые плитки: `<video autoPlay playsInline>` без `muted`; fallback-кнопка «Включить звук», если `play()` отклонён.
  - _Requirements: 11, 12, 37, US-6, US-13, Design: §4.2, §8.7_

## Фаза 3. Клиент: WebRTC mesh

- [x] 14. **`MeshConnectionManager`: создание соединений и обмен SDP** · `Frontend`
  - Набор `RTCPeerConnection` по одному на участника; оффер шлёт только старожил.
  - 14.1. `createConnection(peerId, {asInitiator})`: `addTransceiver('audio')` и `addTransceiver('video')` **всегда**, затем `replaceTrack` имеющимися дорожками.
  - 14.2. Инициатор по `peer-joined`: `createOffer` → `setLocalDescription` → `signal:offer`.
  - 14.3. Новичок по ack: создаёт соединения заранее и **ждёт** оффер; на `signal:offer` → `createAnswer` → `signal:answer`; на `signal:answer` → `setRemoteDescription`.
  - _Requirements: 10, US-6, Design: §3.4, §3.5, §4.2, §7.2, §7.3_

- [x] 15. **ICE: обмен кандидатами и удалённые потоки** · `Frontend`
  - Кандидаты не теряются, потоки доезжают до плиток.
  - 15.1. `onicecandidate` → `signal:ice`; входящие → `addIceCandidate`.
  - 15.2. Буфер кандидатов, пришедших до `setRemoteDescription`, со сливом после его применения.
  - 15.3. `ontrack` → событие `remote-stream` → `srcObject` соответствующей плитки.
  - 15.4. Проверка вручную: две вкладки видят и слышат друг друга.
  - _Requirements: 10, 11, US-6, Design: §4.4, §6.3, §7.2, §9.2_

- [x] 16. **Разрыв соединения и деградация одной плитки** · `Frontend`
  - Ломается одно соединение, а не приложение.
  - 16.1. `peer-left` → `pc.close()`, очистка буферов, удаление плитки.
  - 16.2. `iceconnectionstatechange === 'failed'` → плашка «Не удалось установить соединение» **на конкретной плитке**; остальные плитки и чат продолжают работать. ICE-restart не делаем.
  - 16.3. Cleanup в `useEffect`: закрытие всех соединений, обнуление `srcObject`.
  - _Requirements: 31, 34, US-11, US-13, Design: §8.5, §7.6, §13 (R-11)_

## Фаза 4. Клиент: управление устройствами

- [x] 17. **Тумблер микрофона** · `Frontend`
  - Мгновенное переключение через `track.enabled` и индикация у остальных.
  - 17.1. `ControlBar.jsx`: кнопка микрофона, `toggleMic()` → `audioTrack.enabled = !enabled`.
  - 17.2. Отправка `media-state`; на плитке участника с выключенным микрофоном — иконка перечёркнутого микрофона (своя и чужая).
  - 17.3. Кнопка задизейблена, если микрофона нет или доступ не дан.
  - _Requirements: 15, 16, US-7, Design: §3.5, §6.3_

- [x] 18. **Тумблер камеры: гасим лампочку** · `Frontend`
  - Ключевое требование задания: выключение камеры освобождает устройство, аппаратный индикатор гаснет.
  - 18.1. Выключение: `videoTrack.stop()` + `sender.replaceTrack(null)` на **каждом** соединении. `enabled = false` не использовать.
  - 18.2. Включение: новый `getUserMedia({video})` + `sender.replaceTrack(newTrack)` на каждом соединении; пересогласования нет.
  - 18.3. Обновление self-view: замена дорожки в общем `MediaStream` и переприсваивание `srcObject`.
  - 18.4. Заглушка: силуэт человека + имя на месте видео у всех, у кого камера выключена, отсутствует или недоступна.
  - 18.5. **Отображение потери устройства (требование 20).** Срабатывание `ended` из задачи 11.3 приводит к тому же визуальному результату, что и ручное выключение: у себя и у остальных на плитке силуэт с именем, тумблер переходит в состояние «выключено» и дизейблится, на своей плитке дополнительно плашка «Устройство недоступно».
  - 18.6. Проверка вручную: **лампочка камеры физически гаснет**, обратное включение возвращает видео без переподключения.
  - _Requirements: 17, 18, 19, 20, US-7, US-12, Design: **§3.5**, §7.4, §8.4, §13 (R-2, R-3)_

## Фаза 5. Клиент: чат, участники, выход

- [x] 19. **Панель чата** · `Frontend`
  - Отправка, история, время, автопрокрутка, системные строки.
  - 19.1. `ChatPanel.jsx`: список сообщений, поле ввода, отправка по Enter; пустое или пробельное сообщение не отправляется.
  - 19.2. Имя отправителя и время `HH:MM` по локальному времени через `Intl.DateTimeFormat` из `ts`.
  - 19.3. История из ack `join` рендерится один раз; новые сообщения добавляются по `chat:message`.
  - 19.4. Системные строки: «<Имя> в комнате» / «<Имя> больше не в комнате» — отдельным стилем, без глагола (род имени приложению неизвестен).
  - 19.5. Автопрокрутка вниз при новом сообщении (`useAutoScroll`).
  - 19.6. Весь текст рендерится только как children в JSX; `dangerouslySetInnerHTML` не используется.
  - _Requirements: 21, 22, 23, 24, 25, 39, US-8, US-9, Design: §4.2, §7.5, §10.2_

- [x] 20. **Список участников и ссылка-приглашение** · `Frontend`
  - Актуальный состав комнаты и способ позвать остальных.
  - 20.1. `ParticipantList.jsx` по событию `participants`, счётчик «N из 4»; внутренние id нигде не показываются.
  - 20.2. Кнопка копирования ссылки (`navigator.clipboard`) с подтверждением «Ссылка скопирована» и fallback-полем на случай отказа Clipboard API.
  - _Requirements: 3, 26, 30, US-3, US-9, Design: §4.2, §5.4_

- [x] 21. **Выход из комнаты** · `Frontend`
  - Осознанный выход и закрытие вкладки приводят к одному результату.
  - 21.1. Кнопка «Выйти»: `leave` → `stopAll()` → закрытие соединений → возврат на стартовый экран.
  - 21.2. Закрытие вкладки обрабатывается сервером как `disconnect` (клиентских костылей не добавляем); перезагрузка — новый вход с повторным вводом имени.
  - _Requirements: 27, 28, 29, US-10, US-11, Design: §7.6_

- [x] 22. **Экраны ошибок и состояний** · `Frontend`
  - Ни один сбой не заканчивается белым экраном.
  - 22.1. `Notice.jsx` и подключение состояний: «Комната заполнена» + кнопка «Повторить вход»; «Нет доступа к камере/микрофону» с подсказкой; «Не удалось подключиться к серверу»; «Соединение с сервером потеряно»; «Браузер не поддерживает WebRTC»; «Устройство недоступно».
  - 22.2. Проверка: при выключенном сервере клиент показывает понятное сообщение, а не падает.
  - _Requirements: 8, 33, 35, 36, US-5, US-12, US-13, Design: §8.1, §8.2, §8.3, §8.6_

- [x] 23. **Стили и раскладка** · `Frontend`
  - «Работает и понятно»: читаемость и очевидность элементов управления важнее эстетики.
