# Видеочат-комната

Групповой видеозвонок до четырёх участников со встроенным текстовым чатом.
Открыл ссылку, представился — и ты в звонке: ни регистрации, ни установки.

Медиа идёт напрямую между браузерами (WebRTC, топология mesh), сервер на
Node.js отвечает только за сигналинг, чат и состав комнат.

Требования и решения описаны в [`prds/video-chat-room/`](./prds/video-chat-room/):
[PRD](./prds/video-chat-room/prd-video-chat-room.md) — что и зачем,
[Technical Design](./prds/video-chat-room/design-video-chat-room.md) — как и почему
именно так, [Implementation Plan](./prds/video-chat-room/impl-video-chat-room.md) —
порядок работ.

---

## Требования к окружению

- **Node.js 20 LTS или новее** (проверьте: `node -v`), npm 10+ — используются
  workspaces.
- Браузер с поддержкой WebRTC: Chrome, Firefox или Edge версии 100+.
- Камера и микрофон — необязательны: без них участник всё равно входит в комнату,
  просто с выключенными устройствами.

## Установка

```bash
npm install
```

Одна команда на весь проект: `server` и `client` — npm workspaces одного корня.

## Запуск в режиме разработки

```bash
npm run dev
```

Поднимаются два процесса: сервер на `http://localhost:3001` и Vite на
`http://localhost:5173`. Открывать нужно **5173** — Vite проксирует туда
сигналинг, поэтому и страница, и сокет живут на одном origin.

## Запуск в production

```bash
npm run build
npm start
```

`build` собирает клиент в `client/dist`, `start` поднимает один процесс на
`http://localhost:3001`: он же отдаёт статику, он же обслуживает сигналинг.
Прямой заход по ссылке-приглашению `http://localhost:3001/<roomId>` возвращает
приложение, а не 404.

Порт меняется переменной окружения: `PORT=8080 npm start`.

Скрипт `start` выставляет `NODE_ENV=production` синтаксисом POSIX-оболочки. В
Windows-консоли (`cmd`) запускайте сервер как
`set NODE_ENV=production && node server/src/index.js`.

## Проверка

```bash
npm test
npm run lint
```

`test` — серверные unit- и интеграционные тесты (реальный Socket.io на свободном
порту) плюс компонентные тесты React в jsdom. `lint` — ESLint на оба пакета;
правило `react/no-danger` включено как ошибка, потому что `dangerouslySetInnerHTML`
— единственный способ пронести XSS через чат, и держаться запрет должен проверкой,
а не памятью.

## HTTPS и localhost

`getUserMedia` и WebRTC работают только в защищённом контексте (secure context).

**Почему так.** Камера и микрофон — это доступ к физическому окружению человека,
и однажды выданное разрешение браузер запоминает для origin. По обычному HTTP
трафик идёт открытым текстом и никем не подписан, поэтому любой посредник на пути
— публичный Wi-Fi, провайдер, подменённый DNS — может выдать себя за ваш сайт или
дописать свой код в страницу. Тогда чужой скрипт получил бы уже выданное вами
разрешение и включил камеру. Требование HTTPS закрывает именно это: шифрование
плюс сертификат дают гарантию, что страница пришла от того origin, которому вы
доверились, и что по дороге её не переписали. Поэтому спецификация относит
`getUserMedia` к powerful features, доступным только в защищённом контексте.

**Почему `localhost` считается защищённым.** Угроза, от которой защищает HTTPS, —
это посредник на сетевом пути. У запроса на `localhost` сетевого пути нет: он не
покидает машину и не проходит ни через один узел, который можно было бы
перехватить или подменить. Перехватить его может только тот, кто уже выполняет код
на этой же машине, — а против такого противника сертификат всё равно бессилен.
Поэтому браузеры относят `http://localhost` и `127.0.0.1` к доверенным
источникам, и локальная разработка не требует сертификата.

А вот при проверке с другого устройства в локальной сети — по адресу вида
`http://192.168.1.10:3001` — защищённого контекста уже нет: браузер не отдаст
камеру и микрофон. Варианты:

- **`mkcert`** — локальный доверенный сертификат на IP или имя хоста, и сервер
  поднимается по HTTPS;
- **туннель** (`ngrok`, `cloudflared`) — публичный HTTPS-адрес, проксирующий на
  локальный порт. Проще, если нужно быстро показать работу с чужого устройства.

## Архитектурные решения

Кратко; подробно с обоснованиями — в
[Technical Design](./prds/video-chat-room/design-video-chat-room.md).

- **Mesh, а не SFU.** Каждый участник держит прямое соединение с каждым: на
  четверых — 6 соединений. Медиасервера нет, и именно поэтому лимит комнаты — 4.
- **Socket.io только как сигналинг.** Сервер перекладывает SDP и ICE, не разбирая
  их, и ведёт чат со списком участников. Медиа через него не проходит.
- **Оффер инициирует старожил, новичок отвечает.** Роль назначается однозначно —
  так не бывает встречных офферов и не нужен «вежливый пир».
- **Проверка лимита атомарна.** Условие «меньше четырёх» и вставка участника
  выполняются в одном синхронном блоке без единого `await`: два одновременных
  входа на последний слот не могут оба пройти.
- **Камера выключается `track.stop()` плюс `replaceTrack(null)`, микрофон —
  `track.enabled`.** Асимметрия осознанная: только остановка дорожки гасит
  аппаратную лампочку камеры, а микрофону мгновенное переключение важнее.
- **Состояние комнат — в памяти процесса.** Ни базы, ни файлов. Комната живёт,
  пока в ней есть хотя бы один участник; с уходом последнего исчезают и комната,
  и её история чата. Вход по тому же адресу создаёт новую пустую комнату.
- **На клиенте не сохраняется ничего.** Ни `localStorage`, ни `sessionStorage`:
  после перезагрузки имя вводится заново.

## Что считается ожидаемым поведением

- **Перезапуск сервера уничтожает активные комнаты.** Состояние живёт только в
  памяти процесса, поэтому после рестарта все участники получают «Соединение с
  сервером потеряно» и входят заново. Это не дефект, а следствие отказа от базы.
- **Автопереподключения нет.** Выпавший из-за обрыва участник возвращается только
  повторным входом по ссылке.
- **TURN не используется.** Пара за строгим симметричным NAT может не соединиться
  — тогда деградирует одна плитка, а не весь звонок.
- **Вкладка — отдельный участник.** Две вкладки одного человека занимают два слота
  из четырёх.
